* Einleitung
Dieses Dokument beschreibt die Architektur, Pinbelegung und Funktionsweise
der STM32F411‑basierten Game‑Plattform.

Das Projekt gliedert sich in zwei Teile:

- Eine wiederverwendbare *Engine* (=include/=, =src/=) - Takt, Display,
  Framebuffer, Sprites, Text, Joystick, Audio, sowie die *GameAPI*
  (=include/game.h=), über die jedes Spiel angeschlossen wird.
- Mehrere eigenständige *Beispiele* unter =examples/=, die jeweils die
  Engine plus ihre eigenen, spielspezifischen Dateien zu einer Firmware
  bauen.

Dieses Dokument dient als Entwicklerhandbuch für Wartung, Erweiterung und
Debugging - sowohl der Engine als auch neuer, eigener Spiele darauf.

** Build-System
Das Wurzel-=Makefile= baut kein eigenes Firmware-Image - es iteriert nur
über =EXAMPLES= und ruft =make -C examples/<name>= auf:

#+BEGIN_SRC text
make          baut alle Beispiele (jedes bekommt sein eigenes firmware.elf/.bin)
make clean    räumt alle Beispiele auf
make flash    flasht examples/dig-demo (Standard); für ein anderes Beispiel:
              make -C examples/<name> flash
make docs     erzeugt die Doxygen-Dokumentation (docs/html, docs/latex)
#+END_SRC

Jedes Beispiel hat ein eigenes, eigenständig lauffähiges Makefile
(=examples/<name>/Makefile=), das die Engine-Quellen aus =../../src=
zusammen mit den eigenen =*.c=-Dateien kompiliert:

#+BEGIN_SRC makefile
SRC  = $(wildcard ../../src/*.c) $(wildcard *.c)
CFLAGS += -I../../include -I.
#+END_SRC

D.h. ein neues Beispiel anzulegen bedeutet: neuen Ordner unter
=examples/=, das Makefile-Muster eines bestehenden Beispiels kopieren,
eigenes =main.c= mit einer =GameAPI=-Instanz schreiben (siehe
[[*GameAPI (=include/game.h=)]]), und im Wurzel-=Makefile= zu =EXAMPLES=
hinzufügen.

libopencm3 ist als Git-Submodul eingebunden (=.gitmodules=), nicht als
Kopie - =git submodule update --init= nach dem Klonen nicht vergessen.

* Pinbelegung (STM32F411)
** Übersicht
| Funktion          | Pin  | Richtung | Peripherie      | Beschreibung             |
|-------------------+------+----------+-----------------+--------------------------|
| ILI9488 CS        | PA4  | Output   | GPIO            | Chip Select LCD          |
| ILI9488 DC        | PA3  | Output   | GPIO            | Data/Command             |
| ILI9488 RESET     | PA2  | Output   | GPIO            | Display Reset            |
| SPI1 SCK          | PA5  | AF5      | SPI1            | Display-Takt             |
| SPI1 MOSI         | PA7  | AF5      | SPI1            | Display-Daten            |
| SPI1 MISO         | PA6  | -        | SPI1 (unbenutzt) | frei                     |
| Audio PWM Out     | PB4  | AF2      | TIM3_CH1        | PWM-Audio (bewusst *nicht* PA6 - lag dort direkt zwischen SPI1 SCK/MOSI und hat den Display-Link per Übersprechen gestört, siehe =include/sfx.h=) |
| Joystick UP       | PB13 | Input    | GPIO            | Pull-Up                 |
| Joystick DOWN     | PB15 | Input    | GPIO            | Pull-Up                 |
| Joystick LEFT     | PB14 | Input    | GPIO            | Pull-Up                 |
| Joystick RIGHT    | PB10 | Input    | GPIO            | Pull-Up                 |
| Joystick BUTTON   | PB12 | Input    | GPIO            | Pull-Up                 |
| Joystick ADC X    | PA0  | Analog   | ADC1_IN0        | X-Achse                 |
| Joystick ADC Y    | PA1  | Analog   | ADC1_IN1        | Y-Achse                 |

Alle Konstanten liegen in den jeweiligen Modul-Headern
(=include/ili9488.h=, =include/spi.h=, =include/sfx.h=,
=include/joystick.h=) - dort nachschlagen, nicht hier, falls sich mal
etwas ändert.

** Hinweise
- Alle Display-/Audio-/SPI-Pins liegen auf Port A, alle Joystick-Buttons
  auf Port B.
- Audio-PWM (PA6) nutzt TIM3_CH1 → APB1-Timer (verdoppelte Clock).
- Joystick-Buttons sind *active low* (Pull-Ups); =JS_PORT=/=JS_*_PIN=
  in =joystick.h=.
- ADC-Kanäle nutzen 12-Bit-Auflösung, Sample-Time 144 Zyklen
  (=adc.c=, =ADC_SMPR_SMP_144CYC=).
- Eine SD-Karten-Anbindung ist *nicht* implementiert (kein Treiber im
  Quellbaum) - falls das Board dafür verdrahtet ist, wäre das eine
  Erweiterung über =spi.h= (siehe [[*Erweiterungsmöglichkeiten]]).

* Systemstart & Zeitbasis (=clock.h=/=clock.c=)
** clock_setup()
Initialisiert den Systemtakt auf 100 MHz.

- Aktiviert HSE (25 MHz)
- Konfiguriert PLL:
  - PLLM = 25
  - PLLN = 200
  - PLLP = 2 → 100 MHz SYSCLK
  - PLLQ = 4 → 50 MHz USB/SDIO
- AHB = /1 (100 MHz), APB1 = /2 (50 MHz), APB2 = /1 (100 MHz)
- Setzt Flash-Waitstates (3 WS), schaltet auf PLL um
- Aktualisiert =rcc_ahb_frequency=/=rcc_apb1_frequency=/=rcc_apb2_frequency=

** systick_setup()
Konfiguriert SysTick auf 1 ms-Ticks (Reload = 100000-1, Clocksource = AHB).

** sys_tick_handler()
Wird jede Millisekunde aufgerufen und erhöht nur den internen Zähler
=ms_ticks=. *Steuert nicht die Audio-Engine* - die läuft über einen
eigenen TIM2-Interrupt bei 20 kHz (siehe [[*Audio-Engine (=include/sfx.h=/=include/music.h=)]]).

** millis() / delay_ms(ms)
=millis()= liefert den aktuellen Millisekunden-Zähler (überlaufsicher
per Differenzbildung nutzbar). =delay_ms()= ist ein Busy-Wait darauf,
u.a. für die Reset-Sequenz des Displays genutzt.

* GameAPI (=include/game.h=)
Das ist die zentrale Abstraktion, über die jedes Spiel an die Engine
angeschlossen wird - jedes der vier Beispiele unter =examples/= besteht
im Kern aus genau dieser Struktur plus =main()=:

#+BEGIN_SRC c
typedef struct {
    const char *name;
    void (*init)(void);
    void (*update)(const JoystickState *js, uint32_t tick_ms);
    void (*draw)(void);
} GameAPI;

void game_run(const GameAPI *game, uint32_t tick_ms);
#+END_SRC

=game_run()=

1. initialisiert Takt, SysTick, Display, Framebuffer-Palette und Joystick,
2. ruft einmalig =game->init()= auf,
3. läuft danach endlos: fragt den Joystick ab, ruft =game->update()= alle
   =tick_ms= Millisekunden auf (mit Nachhol-Ticks, falls ein Frame mal
   länger als =tick_ms= gedauert hat - die Spielgeschwindigkeit bleibt
   damit ans Wall-Clock gebunden statt an die Bildrate, mit einer festen
   Obergrenze von 5 Nachhol-Ticks pro Frame als Absicherung), ruft
   =game->draw()= *jede* Schleifeniteration auf (der Framebuffer ist zu
   diesem Zeitpunkt bereits mit Farbe 0 gelöscht) und schiebt das Bild
   per =fb8_flush_dma()= raus.

Ein Spiel ruft =clock_setup()=/=ili9488_init()=/etc. also *nie* selbst
auf - das übernimmt =game_run()=.

** Wahl von tick_ms
=tick_ms= bestimmt, wie oft =update()= läuft - nicht, wie oft gezeichnet
wird (das passiert immer, jede Iteration). Die drei kachelbasierten
Beispiele (dig-demo, Zauberschloss, Grogs Revenge) bewegen ihre Figur in
festen 16px-Schritten alle 150 ms - fühlt sich wie klassische
Raster-Bewegung an. Das scroller-demo-Beispiel nutzt dagegen 30 ms, damit
sich Position/Physik nah an jedem Frame ändert und die Kamera als
flüssiges Scrollen statt als Raster-Sprünge wirkt (siehe
[[*scroller-demo - echtes Side-Scrolling (Proof of Concept)]]).

* Framebuffer (=include/framebuffer8.h=)
4-Bit-indizierter Framebuffer, 480×320 Pixel, 2 Pixel pro Byte
(Palettenindex 0-15 in =fb8_palette[16]=, RGB565).

Ursprünglich 320×240 bei 1 Byte/Pixel (256 Farben, wie es der Name
=framebuffer8= noch nahelegt - historisch gewachsen, nicht mehr
korrigiert). Beim Umstieg auf das größere 480×320-Panel hätte 1
Byte/Pixel 153.600 statt 76.800 Byte gebraucht und damit nicht mehr in
die 128 KB RAM des STM32F411CE gepasst. Da Sprites/Tiles ohnehin nie
mehr als die 16 Basisfarben genutzt haben, packt der Framebuffer jetzt
2 Pixel/Byte (4 Bit/Pixel) - exakt wieder 76.800 Byte, nur über die
größere Fläche verteilt.

#+BEGIN_SRC c
#define FB8_WIDTH   480
#define FB8_HEIGHT  320

void fb8_clear(uint8_t color);
void fb8_set_pixel(int x, int y, uint8_t color);
uint8_t fb8_get_pixel(int x, int y);
void fb8_fill_rect(int x, int y, int w, int h, uint8_t color);
void fb8_init_palette(void);
void fb8_flush(void);       // gepollt, Referenzimplementierung
void fb8_flush_dma(void);   // DMA-basiert, deutlich schneller - der Normalfall
#+END_SRC

=fb8_init_palette()= belegt alle 16 Paletteneinträge mit einer
C64-artigen Farbpalette (Schwarz, Weiß, Rot, Cyan, Lila, Grün, Blau,
Gelb, Orange, Braun, Hellrot, Dunkelgrau, Grau, Hellgrün, Hellblau,
Hellgrau) - alle Beispiele nutzen diese Indizes konsistent.

=fb8_flush_dma()= konvertiert Zeile für Zeile in einen RGB565-Zwischen-
puffer und schiebt ihn per DMA2/Stream3 über SPI1 raus (siehe
[[*SPI-Abstraktion (=include/spi.h=)]]) - das ist der teuerste Schritt
jeder Frame und damit die praktische Obergrenze für die erreichbare
Bildrate, unabhängig von =tick_ms=.

* Sprite-Engine (=include/sprite16.h=)
Ein einziges, festes Sprite-Format für die ganze Engine: 16×16 Pixel,
1 Byte/Pixel (Palettenindex, 0 = transparent).

#+BEGIN_SRC c
typedef struct {
    uint8_t px[16][16];
} sprite16_t;

void draw_sprite16(int x, int y, const sprite16_t *spr);
#+END_SRC

=draw_sprite16()= zeichnet an *beliebigen* Pixelkoordinaten (nicht nur
auf ein 16px-Raster) und klippt automatisch an den Framebuffer-Rändern.
Genau das macht das scroller-demo-Beispiel möglich, ohne dass an der
Engine etwas geändert werden musste - siehe
[[*scroller-demo - echtes Side-Scrolling (Proof of Concept)]].

* Text-Rendering (=include/text.h=)
#+BEGIN_SRC c
void draw_char(int x, int y, char c, uint8_t color);
void draw_text(int x, int y, const char *s, uint8_t color);
#+END_SRC

Fester 8×8-Font (=font8x8_basic=, ASCII 32..127, siehe
=include/font8x8.h=). Zeichen außerhalb dieses Bereichs werden als =?=
dargestellt. *Es gibt keine Umlaute/ß* - alle Beispiele schreiben
deutschen Text deshalb transliteriert (UE/OE/AE/SS), wie viele
8-Bit-Spiele ihrer Zeit.

Ein zweiter, ungenutzter 6×8-Font liegt unter =include/font6x8.h= bereit
(z. B. für kompakteren HUD-Text in einem künftigen Spiel).

* Display-Treiber ILI9488/ILI9486 (=include/ili9488.h=)
Löste den ursprünglichen ST7789-Treiber ab, als das Panel auf 480×320
vergrößert wurde. Gleiche Steuerpins, gleicher MIPI-DBI-kompatibler
Befehlssatz (0x2A/0x2B/0x2C für die Fensteradressierung).

#+BEGIN_SRC c
void ili9488_init(void);
void ili9488_set_window(uint16_t x0, uint16_t y0, uint16_t x1, uint16_t y1);
void ili9488_draw_pixel(uint16_t x, uint16_t y, uint16_t color);
void ili9488_fill_rect(uint16_t x, uint16_t y, uint16_t w, uint16_t h, uint16_t color);
void ili9488_cmd(uint8_t cmd);
void ili9488_data(uint8_t data);
#+END_SRC

=ili9488_init()= ruft =spi1_setup()= auf (siehe unten), macht die
Reset-Sequenz über den RST-Pin und initialisiert das Panel: Gamma-,
Power- und VCOM-Register, MADCTL (Querformat), COLMOD (16bpp RGB565),
Sleep Out, Display On.

*Wichtig:* Auf dem einen konkret verbauten Panel hat sich das COLMOD
auf 16bpp/RGB565 als nötig herausgestellt statt der 18bpp/RGB666
(3 Byte/Pixel), die "echte" ILI9488-Module über SPI oft brauchen -
Symptom bei RGB666 war ein durchlaufender/springender Bildinhalt
(alter oberer Bildbereich blutete in den unteren durch), weil der
Controller die Pixeldaten offenbar als 16bpp interpretiert und sein
Adresszähler dadurch vor Ende des Frames umlief. Sehr wahrscheinlich
steckt in dem als "ILI9488" verkauften Modul tatsächlich ein ILI9486 -
ein bei günstigen 3.5"-SPI-TFT-Modulen häufiges Mislabeling. Da PA6
(SPI1 MISO) nicht angeschlossen ist, lässt sich die Controller-ID nicht
per Software auslesen; falls ein anderes Panel verbaut wird, ist das
COLMOD/Pixelformat (=ili9488_init()=, =fb8_flush()=/=fb8_flush_dma()=
in =src/framebuffer8.c=) der erste Ansatzpunkt bei Bildfehlern.

* SPI-Abstraktion (=include/spi.h=)
Ein einziger, geteilter SPI1-Treiber - alles, was SPI1 nutzt (aktuell
nur das Display), ruft =spi1_setup()= einmal auf und nutzt danach
=spi1_write8()=/=spi1_write_buf()=/=spi1_write_buf_dma()=.

#+BEGIN_SRC c
void spi1_setup(uint32_t baudrate_div);
void spi1_write8(uint8_t data);
void spi1_write_buf(const uint8_t *buf, uint32_t len);
void spi1_write_buf_dma(const uint8_t *buf, uint32_t len);
#+END_SRC

Die DMA-Variante nutzt DMA2 Stream3 Channel3 (SPI1_TX), blockiert bis
=DMA_TCIF= gesetzt ist, und wird von =fb8_flush_dma()= für den
Framebuffer-Transfer genutzt.

* ADC-Abstraktion (=include/adc.h=)
Kleiner, generischer ADC1-Wrapper (gepollt, Einzelkonvertierung),
ursprünglich aus dem Joystick-Treiber herausgezogen, damit er auch für
andere Analogeingänge wiederverwendbar ist:

#+BEGIN_SRC c
void hal_adc_init(void);
void hal_adc_pin_setup(uint32_t gpioport, uint16_t gpio_pin);
uint16_t hal_adc_read(uint8_t channel);
#+END_SRC

* Joystick-Subsystem (=include/joystick.h=)
#+BEGIN_SRC c
typedef struct {
    uint8_t raw;       // aktuell gehaltene Tasten (JS_*-Bitmaske)
    uint8_t pressed;   // Flanke: gerade gedrückt
    uint8_t released;  // Flanke: gerade losgelassen
    uint8_t repeat;     // Auto-Repeat-Puls
} JoystickState;

void joystick_init(void);
JoystickState joystick_update(void);
uint16_t joystick_get_adc_x(void);
uint16_t joystick_get_adc_y(void);
#+END_SRC

Fünf digitale Tasten (UP/DOWN/LEFT/RIGHT/BTN, active low mit Pull-Up)
plus zwei analoge Achsen.

- invaders nutzt als einziges Beispiel die analoge X-Achse
  (=joystick_get_adc_x()=) für die Bewegung - proportional mit
  Totzone statt der binären Pfeiltasten, siehe
  [[*invaders - Space-Invaders-artiges Shoot-em-up]]. Die übrigen vier
  Beispiele nutzen ausschließlich die fünf digitalen Tasten.
- In dig-demo, Zauberschloss und Grogs Revenge bewegen die Pfeiltasten
  die Spielfigur um genau ein Tile pro Logik-Tick; BTN löst eine
  kontextabhängige Aktion auf dem Feld aus, dem die Figur zugewandt ist
  bzw. an dem sie steht (Gegenstand aufheben, Tür aufschließen, kämpfen,
  Zoll bezahlen) - das joystick-taugliche Äquivalent zu den
  Zwei-Wort-Textkommandos der Originale.
- Im scroller-demo bewegen LEFT/RIGHT die Figur kontinuierlich
  (pixelweise, auch in der Luft), UP oder BTN springt.

* Audio-Engine (=include/sfx.h=/=include/music.h=)
** sfx.h - Pseudo-SID-Synthesizer
Ein kleiner 3-Stimmen-Synthesizer, der einen PWM-Lautsprecherausgang
ansteuert: TIM3 erzeugt die ~40 kHz PWM-Trägerfrequenz auf PA6, TIM2
läuft mit 20 kHz und treibt bei jedem Interrupt den Stimmen-Mixer
(=sid_update()= in =sfx.c=) - *nicht* SysTick.

#+BEGIN_SRC c
typedef enum {
    SFX_NONE = 0, SFX_BEEP, SFX_LASER, SFX_EXPLOSION,
    SFX_NOISE_SHORT, SFX_PICKUP, SFX_MOVE,
} SfxType;

void sfx_init(void);
void sfx_update_1ms(void);   // interner 1ms-Tick, wird aus dem TIM2-ISR abgeleitet
void sfx_play(SfxType type); // Stimme 1: kanonische Effekte
void sfx_stop(void);
void sfx_play_freq(uint16_t freq);       // Stimme 0: rohe Frequenz, für music.h
void sfx_play_bass_freq(uint16_t freq);  // Stimme 2: optionaler Bass, für music.h
#+END_SRC

Jede Stimme hat eine Wellenform (Rechteck/Dreieck/Rauschen via LFSR),
Frequenz, Lautstärke und Phasenakkumulator; die Mischung wird pro
20-kHz-Sample auf den PWM-Tastgrad abgebildet. Die Frequenz-zu-Phasen-
Schrittweite wird als Q16-Fixpunkt-Multiplikator vorab berechnet
(=SID_STEP_PER_HZ_Q16=), damit zur Laufzeit keine 64-Bit-Division nötig
ist (der Cortex-M4 hat dafür keine Hardware, und =-nostdlib= verlinkt
kein =libgcc= für den Softwarepfad).

Drei Verbesserungen gegenüber einem reinen "Ton an/Ton aus":

- *Hüllkurve*: jede Stimme hat neben =volume= (Zielpegel) ein =env=
  (aktueller, tatsächlich gehörter Pegel), das =envelope_tick()= pro
  1-ms-Tick Richtung =volume= (Attack, ca. 4 ms) bzw. Richtung 0
  (Release, ca. 20 ms) rampt, statt hart zu schalten - der Mixer
  benutzt =env=, nicht =volume=. Das nimmt jedem Effekt- und Notenende
  das hörbare Klicken; =sfx_play_freq(0)=/=sfx_play_bass_freq(0)= lösen
  jetzt ein Ausklingen aus statt eines sofortigen Stopps.
- *Pulsweiten-Modulation*: Rechteckstimmen haben ein =pw= (Tastgrad,
  0..0xFFFF statt fest 50%). =SFX_LASER= läuft den Tastgrad während des
  Frequenz-Sweeps mit hoch - klingt beim Einsatz dünner/schnarrender,
  wird zum Ende voller, ein billiger, aber wirkungsvoller SID-Trick.
- *Dritte Stimme aktiviert*: Stimme 2 war deklariert, aber ungenutzt.
  Jetzt treibt sie wahlweise einen zweiten Musikkanal (siehe
  =music_init_bass()= unten) - ansonsten bleibt sie stumm, bestehender
  Code ohne Bass-Aufruf verhält sich unverändert.

=SFX_PICKUP= ist außerdem kein reiner Sweep mehr, sondern ein kurzes
Zwei-Ton-Arpeggio (C5→G5) - liest sich eher als "Ding-Ding" denn als
Sirene. Und =SFX_BEEP= hatte schlicht keinen =case= in =sfx_play()=s
Switch und fiel auf =default: sfx_stop()= - jeder Aufruf verstummte
also *alle* Stimmen, statt zu piepsen (betraf scroller-demos Sprung-Sound
und zwei Stellen in Zauberschloss). Jetzt spielt er einen sauberen,
kurzen Ton.

** music.h - Noten-Sequencer
Generischer Player für eine =MusicNote[]=-Sequenz über =sfx_play_freq()=
(Stimme 0), optional mit zweitem Kanal über =sfx_play_bass_freq()=
(Stimme 2):

#+BEGIN_SRC c
typedef struct {
    uint16_t freq;      // 0 = Pause
    uint16_t duration;  // ms; duration == 0 markiert Track-Ende (springt zurück auf 0)
} MusicNote;

void music_init(const MusicNote *track);       // Melodie, Stimme 0
void music_init_bass(const MusicNote *track);  // optional: Bass, Stimme 2
void music_update_1ms(void);
void music_stop(void);
#+END_SRC

Melodie und Bass laufen als zwei unabhängige Sequenzer-Instanzen in
=music_update_1ms()= und loopen jeweils eigenständig auf ihrer eigenen
Notenfolge - für einen Bass, der über Loop-Grenzen hinweg synchron zur
Melodie bleibt, muss seine Gesamtdauer (Summe aller =duration=-Werte vor
dem Terminator) zur Melodie-Gesamtdauer passen. =music_init_bass()= ist
rein additiv: ruft ein Spiel es nicht auf, bleibt Stimme 2 stumm und
nichts ändert sich gegenüber vorher.

Die Engine liefert *keine* Musikdaten mit - jedes Spiel bringt seinen
eigenen Track mit. dig-demo tut das in =examples/dig-demo/track.h= +
=track.c=, generiert aus einer MIDI-Datei über
=examples/dig-demo/tools/midi2console.py= (siehe dort das
=README-midi2console.md=). nebelkrone schreibt seinen Track
(=examples/nebelkrone/track.c=) von Hand und nutzt als einziges
Beispiel bislang auch den Bass-Kanal - =nebel_bass[]= sind vier lange
Grundton-Haltetöne (A2/E2/G2/A2) unter den Melodiephrasen.

* Die Beispiele (=examples/=)
Jedes Beispiel ist in sich geschlossen (eigene Tile-IDs, eigene
Pixelkunst, eigenes =main.c= mit einer =GameAPI=-Instanz) und
eigenständig baubar. Gemeinsames Muster: Zustandsautomat (Titel → Spiel
→ Sieg/Game Over), deutschsprachiger UI-Text ohne Umlaute.

** dig-demo - Technik-Demo
Kleine Boulder-Dash-artige Demo auf einer einzelnen Bildschirmkarte
(20×15 Tiles): Spielfigur läuft über die Karte, gräbt Erde frei,
sammelt Diamanten, HUD zeigt Punktzahl/Leben. Zeigt Kachelkarte
(=tiles.h=/=tileset16.h=), Sprites, Sound-Event-Mapping (=sound.h=,
=bd_sound_play()=) und Musik-Wiedergabe im Zusammenspiel.

** zauberschloss - RPG
Angelehnt an das deutsche C64-Adventure „Zauberschloß" (1984, Dennis
Merbach): Krone aus dem verschlossenen Schloss des Zauberers stehlen und
damit entkommen. Vier persistente Räume (=rooms.c=: Eingang, Wachraum,
Schatzkammer, Thronsaal) über eine Nachbarschaftstabelle verbunden -
Zustand pro Raum (offene Türen, besiegte Wache, aufgesammelte
Gegenstände) bleibt beim Verlassen und Wiederbetreten erhalten
(=tiles_select_map()= schaltet nur den aktiven Kartenpuffer um, baut
nichts neu). Rätselkette: Schwert in der Schatzkammer holen → Wache im
Wachraum damit besiegen → Schlüssel findet sich dort → damit die Tür zum
Thronsaal aufschließen → Krone nehmen (weckt den Zauberer, der einen
danach im Thronsaal jagt) → zurück zum Eingang und durchs Tor.

** grogs-revenge - Arcade
Angelehnt an „B.C. II: Grog's Revenge" (C64, 1984, Sydney Development):
Thor reitet auf seinem Steinrad über drei Berge (=mountains.c=,
zunehmend schwieriger), sammelt Muscheln, um Peters Zoll zu bezahlen und
zum nächsten Berg zu gelangen, während Grog ihn jagt (einfache
Greedy-Verfolgung, siehe =grog_update()= in =main.c=) und Felsen/Löcher
den Weg versperren. Vereinfacht gegenüber dem Original: ein Bildschirm
pro Berg (kein seitliches Scrollen innerhalb eines Bergs), keine
separaten dunklen Höhlen-Level, kein zweiter Gegnertyp (Tiredactyl) -
alles mögliche Erweiterungen, siehe unten.

** scroller-demo - echtes Side-Scrolling (Proof of Concept)
Beantwortet die Frage, ob mit dieser Engine *echtes*, pixelgenaues
Side-Scrolling möglich ist (ja) - im Unterschied zu den drei
kachelbasierten Beispielen oben, die sich in festen 16px-Schritten pro
Logik-Tick bewegen.

- =level.h=/=level.c=: ein Höhenfeld pro Spalte (=ground_row[100]=,
  100 Tiles = 1600px breit) plus Hindernis-/Münz-Overlays - deutlich
  breiter als der 320px-Bildschirm.
- Die Kamera (=camera_x=) folgt der Spielfigur in *einzelnen Pixeln*.
  Beim Zeichnen wird der Sub-Tile-Rest (=frac = camera_x % 16=)
  berechnet und jede sichtbare Spalte entsprechend versetzt gezeichnet -
  =draw_sprite16()= musste dafür *nicht* geändert werden, es zeichnet
  schon immer auf beliebigen Pixelkoordinaten.
- =TICK_MS= ist mit 30 statt 150 deutlich kürzer, damit sich Bewegung
  und Schwerkraft-/Sprungphysik nah an jedem Frame ändern und nicht als
  sichtbare Raster-Sprünge wirken.
- Einfache Integer-Physik: Schwerkraft, Sprungimpuls, Boden-Snapping pro
  Spalte (klassisches "Sonic-Style" Höhenfeld statt echter
  AABB-Kollision gegen Wände).

** invaders - Space-Invaders-artiges Shoot-em-up
Klassisches Formations-Shoot-em-up im Stil des Arcade-Originals von
1978, komplett ohne Kachelkarte - alle Sprites werden direkt in
Pixelkoordinaten gezeichnet (=main.c= besteht fast nur aus =game.h=,
=sprite16.h=, =text.h=, =sfx.h=, =joystick.h=).

- Steuerung über die analoge X-Achse des Sticks statt der Pfeiltasten
  (=analog_move_delta()=): Totzone um die Mittelstellung (2048 von
  0..4095, Ruhelage der meisten Joystick-Module) absorbiert Zittern im
  Stillstand, der restliche Weg wird linear auf bis zu
  =PLAYER_MAX_SPEED= px/Tick abgebildet - proportionale statt
  binärer An/Aus-Bewegung. BTN (digital) feuert weiterhin.
- Drei Alien-Typen (Tintenfisch/Krabbe/Krake, je nach Reihe 10/20/30
  Punkte) mit je *zwei Animationsframes*, die bei jedem
  Formations-Schritt umgeschaltet werden (=alien_anim_frame=) -
  klassischer Lauf-Zyklus-Look ohne zusätzliche Engine-Änderungen, rein
  über zwei =sprite16_t=-Konstanten pro Typ.
- Die Alien-Formation bewegt sich als starrer Block
  (=step_formation()=): Bounding-Box wird aus den noch lebenden
  Aliens berechnet, am Bildschirmrand wird die Richtung umgekehrt und
  eine Zeile nach unten gerückt. Das Bewegungsintervall schrumpft mit
  der Zahl verbleibender Aliens - klassisches Beschleunigen zum Ende
  einer Welle hin.
- Vier zerstörbare Schutzschilde (=shield_cell[][][]=, 8×6-Block-Raster
  je Schild) zwischen Kanone und Aliens; sowohl Spieler- als auch
  Alien-Schüsse fressen sich Block für Block hindurch
  (=shield_hit_test()=).
- Zufällig auftauchendes Bonus-UFO oben im Bild (=ufo_update()=) für
  Extrapunkte, plus eine kleine LCG-PRNG (=rng_next()=, keine
  Standardbibliothek unter =-nostdlib= verfügbar) für Schusszeitpunkte
  der Aliens und UFO-Verhalten.
- Explosions-Sprite für getroffene Aliens und die eigene Kanone
  (=explode_ticks=/=player_explode_ticks=, kurze Anzeigezeit statt
  sofortigem Verschwinden).
- Endet die Formation nicht rechtzeitig, sondern erreicht die
  Schutzschild-Linie, ist die Partie sofort vorbei (wie im Original);
  Wellen laufen sonst endlos weiter und werden mit jeder Runde etwas
  tiefer gestartet.
- Animierter Sternenhintergrund (=draw_stars()=/=update_stars()=): 48
  Punkte in drei Tiefenebenen (unterschiedliche Graustufe, unterschiedliche
  Fallgeschwindigkeit für einen einfachen Parallax-Effekt), die pro
  Logik-Tick nach unten wandern und am unteren Rand mit neuer
  Zufalls-x-Position oben wieder einsteigen - läuft auch auf Titel- und
  Game-Over-Bildschirm durch, da =draw_stars()= als Erstes in
  =invaders_draw()= gezeichnet wird, noch vor dem State-Switch.

** nebelkrone - illustriertes Interactive-Fiction-Gamebook
Ein Rollenspiel-Gamebook im Stil der Solo-Abenteuer, die Das Schwarze
Auge selbst als Heftchen veröffentlicht hat: nummerierte
Entscheidungen statt Texteingabe (diese Hardware hat einen Joystick,
keine Tastatur) und Eigenschaftsproben mit einem einzelnen W20 statt
des vollen Pen-and-Paper-Regelwerks. Eine komplett eigene Geschichte
("Die Nebelkrone") - keine Wiedergabe eines veröffentlichten
DSA-Abenteuers, keine Schauplätze/Begriffe aus dem Franchise, nur an
seiner Spielmechanik orientiert.

- =story.h=/=story.c=: die gesamte Handlung ist ein Array von 15
  =Scene=-Knoten (=SCENE_INTRO= .. =SCENE_END_LOSE=), die =main.c=s
  Zustandsautomat abläuft. Vier Knotentypen: =NODE_TEXT= (Illustration
  + Text + UP/DOWN+BTN-Auswahlmenü), =NODE_CHECK= (würfelt automatisch
  eine von drei Heldeneigenschaften - MUT/KLUGHEIT/GEWANDTHEIT - gegen
  einen W20 und verzweigt), =NODE_COMBAT= (rundenbasierter Kampf) und
  =NODE_END_WIN=/=NODE_END_LOSE=.
- =art.h=/=art.c=/=tileset16.c=: dieselbe Kachelraster-Technik, die
  dig-demo/Zauberschloss/Grogs-Revenge für ihre Raumkarten nutzen, hier
  aber als 20×5-Kachelraster (320×80px, oberes Bildschirmdrittel) für
  acht vorkomponierte Illustrationen (Dorf, Sumpf, Turmruine innen/außen,
  Kampf- und Siegkammer, Tod) statt einer begehbaren Karte -
  =draw_scene_bg()= zeichnet einfach das zur aktuellen Szene gehörige
  Raster.
- Schaden ist zentral über =apply_damage()= verdrahtet: jede
  Eigenschaftsprobe kann bei Misserfolg Lebenspunkte kosten, und wenn
  das tödlich ist, springt =apply_damage()= sofort zu einer
  universellen Todes-Szene mit einem zur jeweiligen Ursache passenden
  Sterbetext (Ersaufen im Sumpf, einstürzende Bretter, Kampf verloren,
  ...) - keine einzelne Szene muss ihr eigenes "Tod"-Ziel kennen.
- Rundenbasierter Kampf (=do_combat_action()=) gegen den Moorschrat:
  ATTACKE/FLIEHEN, plus ein optionaler dritter Menüpunkt TRANK, sobald
  ein zuvor in einer Truhe gefundener Heiltrank (=FLAG_POTION=) im
  Inventar ist - Item-Zustand direkt in der Kampf-UI sichtbar.
- Item-/Story-Flags (=StoryFlag=, ein =uint32_t=-Bitfeld) für Fackel,
  Heiltrank und die erbeutete Krone; das Fehlen der Fackel löst beim
  Betreten des finsteren Turminneren eine feste Schadens-Strafe aus -
  ein Grund, vorher beim Dorfältesten vorbeizuschauen, statt eine
  weitere Kartenprüfung im Code zu brauchen.
- Eigener, handgeschriebener Musik-Loop (=track.c=, nicht wie bei
  dig-demo aus MIDI generiert) mit zweistimmigem Bass
  (=music_init_bass()=, siehe
  [[*music.h - Noten-Sequencer]]) sowie sfx.h-Ereignisse für Treffer,
  Fund, Gefahr und Tod.
- =tools/png2tileset.py= (analog zu dig-demos =tools/midi2console.py=
  für Musik): wandelt ein beliebiges Bild offline in ein
  =sprite16_t=-Kachel-Array + Index-Raster um - Farben werden auf die
  16-Farb-Engine-Palette quantisiert (optional mit Floyd-Steinberg-
  Dithering), Transparenz kommt aus dem Alphakanal oder einer
  Chroma-Key-Farbe. Da die Engine weder Bild-Decoder noch Dateisystem
  hat (=-nostdlib=, SD-Karte unimplementiert), ist das der einzige Weg,
  externe Bilder einzubinden - als zur Kompilierzeit mitgebackene
  C-Daten, nicht als Laufzeit-Asset. Siehe
  =tools/README-png2tileset.md=.

** gamebook-template - story-neutrale Vorlage
=main.c= aus nebelkrone ist bewusst datengetrieben - die eigentliche
Geschichte steckt komplett in =story.h=/=story.c=, nichts davon ist in
=main.c= selbst verdrahtet. gamebook-template extrahiert genau diese
Trennung als eigenständiges, lauffähiges Beispiel: dieselbe Engine
(=main.c= praktisch unverändert), aber mit einer bewusst als Platzhalter
erkennbaren Acht-Szenen-Geschichte statt Nebelkrones eigentlichem
Abenteuer - eine Szene pro =NodeKind= (Text mit Verzweigung, Probe,
Gegenstands-Vergabe, Kampf mit Sieg/Flucht-Verzweigung, beide Enden),
gerade genug, um den ganzen Mechanismus einmal durchzuspielen, bevor man
ihn ersetzt.

Was dabei generalisiert wurde, gegenüber der Nebelkrone-spezifischen
=main.c=:

- Titelbildschirm-Text kommt aus =story.h=-Konstanten
  (=GAME_TITLE=/=GAME_TAGLINE=/=GAME_PREMISE_1..3=) statt aus
  hartkodierten Strings in =main.c=.
- Der Heiltrank-Kampfmechanismus heisst jetzt generisch
  =FLAG_HEAL_ITEM= (statt =FLAG_POTION=), mit Menütext, Heilbetrag und
  Trink-Meldung ebenfalls als =story.h=-Konstanten
  (=HEAL_ITEM_LABEL=/=HEAL_ITEM_AMOUNT=/=HEAL_ITEM_USE_MESSAGE=) - wird
  nie benutzt, wenn keine Szene das Flag vergibt.
- Die Sterbemeldung bei einer verlorenen Kampfrunde wird jetzt aus dem
  Gegnernamen zusammengesetzt (=e->name=) statt einen bestimmten
  Monsternamen hart zu kodieren - jeder neue Eintrag in der
  =Enemy=-Tabelle bekommt so automatisch eine passende Meldung.
- Nebelkrones "So nah - die Krone war schon dein"-Zusatzzeile auf dem
  Game-Over-Bildschirm ist eine reine Erzähl-Verzierung fuer genau diese
  eine Geschichte und wurde aus der Vorlage entfernt statt generalisiert
  - genau die Art Detail, die man sich in seiner eigenen Kopie selbst
  wieder dazuschreibt.

Fest im Mechanismus (nicht pro Geschichte konfigurierbar): die drei
Eigenschaften MUT/KLUGHEIT/GEWANDTHEIT, W20-Proben, Kampf gegen
GEWANDTHEIT, die fünf =NodeKind=s. =SCENE_INTRO= und =SCENE_END_LOSE=
sind Pflichtnamen (siehe =story.h=s Kommentar) - jede neue Geschichte
braucht einen Startpunkt und ein universelles Todesziel für
=apply_damage()=.

=art.c=/=art.h=/=tileset16.c= und =track.c=/=track.h= wurden praktisch
unverändert übernommen - die Kachel-Illustrationen (Dorf, Sumpf, Ruine,
Kampf-/Siegkammer, Tod) und der gemäßigte Musik-Loop sind generische
Fantasy-Versatzstücke, keine Nebelkrone-Lore, und taugen als
Startbelegung für eine neue Geschichte genauso wie zum Ersetzen.
=tools/png2tileset.py= liegt ebenfalls bei.

Neue Geschichte anfangen: Ordner nach =examples/<name>/= kopieren, im
Wurzel-=Makefile= zu =EXAMPLES= hinzufügen, dann =story.h=/=story.c=
(und optional Kunst/Musik) ersetzen - siehe
=examples/gamebook-template/README.md= für die Kurzanleitung.

** loderunner - Lode-Runner-artiges Grab-und-Fluchtspiel
Ein Digger-Verfolgungsspiel im Stil von Lode Runner (1983): auf einer
Kachelkarte alles Gold einsammeln und den (dann offenen) Ausgang
erreichen, während Wächter jagen - durch das Graben temporärer Löcher
in Ziegel-Kacheln lassen sich Wächter (oder man selbst, bei
Unachtsamkeit) fangen: wer beim Zufüllen noch im Loch steht, stirbt.
Vereinfacht gegenüber dem Original: keine Seile (Leitern allein
übernehmen die Vertikalbewegung), Wächter nutzen eine gierige
Verfolgungs-Heuristik (dieselbe Idee wie Grogs Verfolgung in
grogs-revenge) statt echter Pfadsuche, kein Steuern in der Luft
während des Fallens.

- Bewegung ist rasterbasiert wie bei dig-demo/grogs-revenge (nicht
  pixelglatt wie scroller-demo): =has_support()= prüft pro Tick, ob die
  aktuelle Position eine Leiter ist oder der Kachel darunter fest ist -
  sonst fällt die Figur automatisch ein Feld pro Tick.
- Graben braucht zwei gleichzeitige Eingaben (Richtung halten + Knopf),
  da der Joystick nur einen Aktionsknopf hat, anders als das Original
  mit getrennten Grab-Links/Grab-Rechts-Tasten. Ziel ist die
  Ziegel-Kachel diagonal unterhalb der gehaltenen Richtung.
- Gegrabene Löcher (=T_HOLE=) sind temporär (=holes[]=, ca. 4,5 s Timer)
  und werden beim Verfallen wieder zu Ziegel - wer zu diesem Zeitpunkt
  noch genau dort steht (Spieler oder Wächter), stirbt; ein
  gefangener Wächter kann in der Zwischenzeit selbststständig
  herausklettern (mit Verzögerung), der Spieler jederzeit per HOCH.
- Drei Level (=levels.c=, nach demselben Muster wie grogs-revenges
  =mountains.c=: =place()=-Hilfsfunktion + Klarstruktur pro Level),
  alle offline mit einem kleinen Python-Simulator derselben
  Bewegungsregeln (Schwerkraft, Leiterklettern, Ziegel/Stahl blockieren)
  auf Erreichbarkeit *ohne Graben* geprüft, bevor sie hier eingetragen
  wurden - Graben ist ein Werkzeug gegen Wächter, keine Voraussetzung,
  um an Gold oder den Ausgang zu kommen.
- Zwei animierte Figuren (Läufer/Wächter, je zwei Lauf-Frames) plus ein
  gemeinsamer Poof-Effekt für Fallen-Tode, wie schon in invaders und
  nebelkrone.

* Erweiterungsmöglichkeiten
Realistische nächste Schritte, sortiert grob nach Aufwand:

- Analogstick auch in den übrigen Beispielen für Bewegung nutzen -
  invaders macht es für die X-Achse bereits vor (=analog_move_delta()=),
  die Y-Achse ist noch ungenutzt.
- grogs-revenge: zweiter Gegnertyp (Tiredactyl), dunkle Höhlen-Level
  (Lichtkegel um die Spielfigur statt volle Sichtbarkeit), echtes
  Scrolling innerhalb eines Bergs (könnte scroller-demos Kamera-Technik
  wiederverwenden).
- zauberschloss: weitere Räume/Etagen, Inventar-Anzeige im HUD statt nur
  J/N-Kürzel.
- scroller-demo: horizontale Wände/Kollision statt reinem Höhenfeld,
  mehrere Level, Gegner.
- invaders: Bullet-vs-Bullet-Kollision (Alienschuss wird vom eigenen
  Schuss abgefangen), Highscore-Speicherung, mehr als ein Spieler-Schuss
  gleichzeitig ab höheren Wellen.
- nebelkrone: weitere Kapitel/Verzweigungen, ein zweiter Gegnertyp,
  Inventar-Anzeige im HUD, Speicherstand für den Spielfortschritt
  zwischen Sitzungen (siehe Speicherstand-Punkt unten - beide Beispiele
  könnten sich dieselbe Persistenz-Lösung teilen).
- SD-Karten-Anbindung über =spi.h= (aktuell nicht implementiert, siehe
  Pinbelegung oben) - z. B. für Level- oder Sprite-Daten von Karte statt
  aus dem Flash.
- Speicherstand (Battery-backed RAM / Flash-Sektor) für Fortschritt
  zwischen Sitzungen.
- Zweiter, austauschbarer Font (=font6x8.h= liegt schon bereit) für
  kompakteren HUD-Text.
- loderunner: Seile (hangelnde Horizontalbewegung) als zweite
  Vertikal-/Diagonal-Mechanik neben Leitern, echte Wächter-Pfadsuche
  statt der gierigen Heuristik, mehr als drei Level.

* Schlusswort
Dieses Dokument beschreibt die Engine (Takt, Display, Framebuffer,
Sprites, Text, Joystick, Audio, GameAPI) sowie die acht Beispiele, die
aktuell darauf aufbauen. Bei Erweiterungen: neue Engine-Funktionalität
gehört nach =include/=/=src/= (allgemeingültig, kein Spielwissen), alles
Spielspezifische in einen neuen oder bestehenden Ordner unter
=examples/=.
